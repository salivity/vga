Programming Copper Style Raster Bars on VGA Hardware

Copper-style color raster chasing—commonly known as "raster bars"—is a visual demoscene technique where the screen background or border dynamically shifts colors scanline by scanline to create glowing, undulating horizontal bands. Originating on the Commodore Amiga via its dedicated "Copper" coprocessor, the effect had to be entirely reinvented on IBM PC Video Graphics Array (VGA) hardware. Because standard VGA lacked a dedicated display-synchronized coprocessor, PC programmers had to force the central CPU to "race the beam" by continuously monitoring the cathode-ray tube (CRT) electron gun's position and rewriting the hardware digital-to-analog converter (DAC) palette registers during horizontal blanking intervals.

The Origin and the VGA Limitation

On the Amiga, the Copper chip executed instructions synchronized directly with the video beam, freeing the Motorola 68000 CPU entirely while changing hardware color registers line by line. Standard IBM VGA hardware provided no such automation. The VGA card operated essentially as a dumb framebuffer paired with an Inmos-compatible palette DAC. To alter colors on a per-scanline basis, the PC’s CPU had to execute tightly timed I/O port writes synchronized to the monitor's horizontal sweep.

The Mechanism of Raster Chasing

Cathode-ray monitors construct images sequentially from left to right, line by line from top to bottom. Between each visible line lies a brief duration called the Horizontal Blanking Interval (HBlank), where the beam shuts off and returns to the left side of the screen. If a programmer changes the color palette precisely during this blanking window, the next drawn scanline will render in the updated color without visual tearing or graphical distortion ("snow"). By continuously shifting color assignments down the screen across subsequent scanlines, a solid color background appears split into smooth, scrolling gradients.

Hardware Registers Involved

Implementing this effect on VGA hardware requires interacting with two primary hardware sub-systems using x86 assembly I/O instructions (IN and OUT):

  1. Input Status Register 1 (Port 0x3DA): This read-only port provides the current state of the video beam. Bit 0 indicates Display Inactive/HBlank when set to 1 (or actively drawing when 0). Bit 3 indicates the Vertical Retrace (VBlank) state, which marks the completion of an entire screen frame.

  2. DAC Palette Address Register (Port 0x3C8) and Data Register (Port 0x3C9): Port 0x3C8 receives the palette index to be modified (commonly index 0, the default overscan/background color). Once selected, three consecutive 6-bit values representing Red, Green, and Blue (ranging from 0 to 63) are sent sequentially to port 0x3C9. The internal address pointer automatically auto-increments after the third write.

The Implementation Pipeline

The implementation relies on an exact polling loop executed entirely in x86 assembly:

  1. Disable Interrupts: The CPU executes CLI (Clear Interrupt Flag). If a timer tick or hardware interrupt fires during the raster loop, the timing drifts, resulting in severe visual jitter.
  2. Synchronize with Vertical Retrace: The CPU polls port 0x3DA, waiting for bit 3 to turn low (if already in retrace) and then high. This establishes a fixed anchor point at the top of the frame.
  3. Wait for Scanline Boundary: The program enters an inner loop reading port 0x3DA:
    • Wait until bit 0 is 0 (ensure the beam is currently drawing pixels, avoiding a mid-blank sync error).
    • Wait until bit 0 flips to 1 (the exact start of the HBlank interval).
  4. Update the Palette: As soon as HBlank is asserted, the CPU immediately outputs the target palette index to port 0x3C8 (if not already set) and writes the new Red, Green, and Blue values to port 0x3C9 using the OUT instruction.
  5. Cycle Padding and Repeat: Because the HBlank window is only a few microseconds wide, the writes must finish before the beam begins the next active scanline. The CPU reads the next set of RGB colors from a precomputed lookup table, repeats the cycle for all remaining visible scanlines, and then re-enables interrupts via STI once the bottom of the screen is reached.

Technical Challenges

The fundamental challenge on VGA hardware was CPU starvation. While the Amiga handled this in background silicon, a PC running copper bars devoted nearly 100% of its CPU cycles to polling I/O ports. Variations in motherboard bus speeds, wait states during port I/O, and CPU clock speeds often required developers to carefully count CPU cycles or calibrate the polling loops dynamically to prevent visual shearing across different IBM PC compatibles.
