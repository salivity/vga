How VGA Mode X Enabled Game Triple Buffering

This article explains how custom, unchained Video Graphics Array (VGA) modes—most notably Mode X—allowed 1990s PC game developers to overcome hardware limitations and implement triple buffering. By bypassing the standard BIOS video modes to reconfigure VGA memory controllers, programmers gained direct access to the full 256 kilobytes of on-board video RAM. This architectural shift allowed multiple distinct framebuffers to reside in video memory at the same time, enabling tear-free animations and smooth frame pacing through instantaneous hardware page flipping.

The Limitations of Standard VGA Mode 13h

In standard DOS game development, the default choice for 256-color graphics was VGA Mode 13h. Mode 13h offered a 320x200 pixel resolution with an easy-to-use linear memory layout: byte 0 in video memory directly corresponded to the top-left pixel on screen.

However, Mode 13h operated in what IBM called "Chain 4" mode. In this mode, the hardware automatically distributed successive pixels across four physical 64 KB memory planes to present a single, contiguous 64 KB address space to the CPU. Because a 320x200 screen requires 64,000 bytes (roughly 62.5 KB), Mode 13h consumed almost the entire addressable space in that memory segment.

This left no room in video memory for secondary display surfaces. Developers either had to draw directly to the visible screen—causing visible tearing and flickering—or render frames into system RAM and copy them to VRAM during the vertical blanking interval (VBLANK), a process that placed heavy demands on the system bus and processor.

Unchaining the VGA: Mode X and Planar Memory

Standard VGA cards were physically equipped with 256 KB of video RAM, divided into four 64 KB planes. To unlock this unused capacity, developers bypassed the standard PC BIOS and wrote directly to VGA registers, creating custom "tweaked" or "unchained" modes, popularized by developer Michael Abrash as Mode X.

By clearing the Chain 4 bit in the VGA Sequencer Memory Mode register (0x3C4, index 0x04) and disabling odd/even addressing, the video hardware exposed all four memory planes at the standard memory address segment 0xA000.

In an unchained planar layout, four consecutive horizontal pixels share the same memory address, with each pixel residing in a different plane:

  • Pixel 0 resides in Plane 0
  • Pixel 1 resides in Plane 1
  • Pixel 2 resides in Plane 2
  • Pixel 3 resides in Plane 3

By selecting the target plane using the Map Mask register (0x3C4, index 0x02), the CPU could access the entire 256 KB of VRAM across the four planes.

VRAM Capacity and Frame Dimensions

Unchaining the memory made the entire 262,144 bytes of VRAM available for frame storage.

When developers configured custom resolutions, they calculated how many complete display pages could fit within this space:

  • Unchained 320x200: A 320x200 resolution requires 64,000 bytes per frame. Dividing 262,144 by 64,000 yields room for 4 full video pages.
  • Mode X (320x240): Mode X typically adjusted the CRT Controller (CRTC) timing registers to produce a 320x240 resolution with square (1:1) pixels. A 320x240 frame requires 76,800 bytes. Dividing 262,144 by 76,800 yields room for 3 full video pages, with 31,744 bytes left over for off-screen sprite or pattern storage.

With at least three full-resolution framebuffers fitting into video memory at once, the physical prerequisite for hardware triple-buffering was established.

Mechanics of Hardware Page Flipping

Rather than copying heavy graphic blocks across the system bus, unchained modes relied on hardware-level display offset modification. The VGA CRT Controller has two 8-bit registers that define where in video memory the video generator begins reading display data:

  1. Start Address High Register (CRTC index 0x0C)
  2. Start Address Low Register (CRTC index 0x0D)

Combined, these registers form a 16-bit offset representing the start address of the current visual frame. By modifying these registers, the programmer instantly moves the monitor's display window to point to another region of VRAM without altering pixel data.

Implementing the Triple-Buffering Scheme

Standard double-buffering introduces a synchronization bottleneck: if the CPU finishes rendering the back buffer before the monitor finishes scanning the current frame, it must pause and wait for the vertical retrace interrupt to swap buffers, leaving CPU cycles unused. If it does not wait, updating the start address mid-scan produces screen tearing.

Custom unchained modes solved this by allocating three buffers across VRAM:

  1. Front Buffer (Display): Currently scanned by the CRT electron beam and visible on the monitor.
  2. Back Buffer (Queued): A completed frame waiting for the next VBLANK to be promoted to the display.
  3. Third Buffer (Drawing): The off-screen buffer where the CPU actively renders the next frame.

The game engine cycled through these three buffers independently of the monitor refresh cycle:

  1. The game logic rendered directly into the Drawing Buffer using planar write modes and the VGA's internal write latches for fast drawing.
  2. Once rendering finished, the Drawing Buffer was tagged as the Queued Buffer, and the previous Queued Buffer became available for drawing the subsequent frame.
  3. The display routine polled the VGA Input Status 1 Register (0x3DA) or used an interrupt handler to detect the start of the Vertical Retrace interval.
  4. During vertical blanking, the CRT Controller's Start Address registers were updated to the base address of the Queued Buffer, making it the Display Buffer without any tearing.

This approach decoupled the game's internal frame rendering rate from the physical monitor refresh rate. The CPU was never forced to idle waiting for an electron beam to finish drawing, maximizing framerates while eliminating visual screen artifacts.
