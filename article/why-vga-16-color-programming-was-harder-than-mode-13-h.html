Why VGA 16-Color Programming Was Harder Than Mode 13h

During the DOS gaming era, developers favored VGA Mode 13h because its linear, byte-per-pixel memory architecture made graphics routines fast and intuitive. In contrast, standard 16-color VGA modes (such as Mode 12h) relied on a planar memory layout that imposed substantial algorithmic overhead. Rendering basic shapes or moving sprites in 16-color modes required manipulating multiple independent bitplanes, managing hardware register states, and performing complex bit-shifting operations to isolate single pixels, turning standard graphics operations into multi-step hardware procedures.

Chunky vs. Planar Architecture

The primary divergence between Mode 13h and 16-color modes lies in how memory maps to the display:

  • Mode 13h (Chunky): A straightforward linear framebuffer where each pixel corresponds directly to one continuous byte in memory. Plotting a pixel at coordinate \((x, y)\) requires calculating Memory_Address = 0xA0000 + (y * 320) + x and writing the color index (0–255) in a single CPU instruction.
  • 16-Color Modes (Planar): Pixels require 4 bits to index 16 colors (often representing Blue, Green, Red, and Intensity). Instead of packing two 4-bit pixels into a single byte, the VGA hardware splits the data across four distinct parallel memory banks called planes. A single byte address across these four planes represents an eight-pixel horizontal strip, with bit 7 of each plane combining to form the 4-bit color value of the first pixel.

Because a single byte in CPU memory space corresponds to eight adjacent pixels at once, direct writes to individual pixels are impossible without disturbing adjacent screen data.

Bit Masking and Read-Modify-Write Overhead

To update a single pixel in a planar mode, the software must perform a read-modify-write cycle using the VGA's internal 32-bit hardware latches:

  1. Read Operation: The CPU reads the target byte address from video memory (0xA000). This read does not return all four planes to the CPU directly; instead, it automatically loads one byte from each of the four planes into the VGA card's internal hardware latches.
  2. Mask Configuration: The program writes to the VGA Graphics Controller registers to set up a bitmask that enables only the specific bit position (0–7) corresponding to the desired pixel.
  3. Write Operation: The CPU writes the new data back to the same memory address. Depending on the active write mode, the VGA mixes the latch contents with the CPU data using the bitmask, preserving the other seven pixels while changing only the target pixel.

This cycle turns a single memory write into a sequence of CPU reads, I/O port writes, and memory writes.

I/O Port Bottlenecks and Write Modes

Manipulating planar memory requires constant communication with the VGA Graphics Controller registers (I/O ports 0x3CE and 0x3CF) and the Sequencer (ports 0x3C4 and 0x3C5). Programmers had to frequently toggle settings like:

  • Plane Mask / Map Mask: Enabling or disabling individual planes during writes.
  • Bit Mask Register: Selecting which of the eight bits within the byte should be modified.
  • Write Modes (0 through 3): Specialized hardware modes for combining CPU data with internal latches, rotating bits, or executing logical operations (AND, OR, XOR).

On x86 architectures, CPU IN and OUT instructions to hardware I/O ports execute significantly slower than normal memory access. Mode 13h completely avoided these port writes during regular frame updates, whereas 16-color routines had to constantly issue I/O instructions to draw primitives or sprites.

Sprite Alignment and Sub-Byte Shifting

In Mode 13h, shifting a sprite horizontally by any number of pixels simply meant adding that offset to the target memory address.

In 16-color planar modes, horizontal sprite movement is split into two distinct algorithmic paths:

  • Byte-Aligned Shifts: Moving a sprite by multiples of 8 pixels allows entire bytes to be transferred plane by plane.
  • Sub-Byte Shifts: Moving a sprite by 1 to 7 pixels requires shifting the bitmap data in software across byte boundaries for every plane before writing. A single 8-pixel-wide segment of a sprite often spans two consecutive bytes in memory when drawn at an arbitrary \(x\)-coordinate, forcing the engine to compute shifts, masks, and merge operations for both the left and right byte segments across all four color planes.

This required either real-time bit shifting, which consumed heavy CPU cycles, or pre-shifting sprites in memory (storing eight variations of every sprite frame), which dramatically increased RAM usage on memory-constrained systems.
