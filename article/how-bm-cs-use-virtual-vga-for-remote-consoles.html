How BMCs Use Virtual VGA for Remote Consoles

Baseboard Management Controllers (BMCs) use integrated virtual Video Graphics Array (VGA) adapters to capture, encode, and transmit a physical server's visual output over the network to a remote administrator. By embedding a dedicated low-power 2D graphics controller directly into the management processor, the BMC provides continuous access to the server’s display output from power-on through operating system execution. This out-of-band architecture enables full keyboard, video, and mouse (KVM) redirection even if the host operating system crashes or lacks network connectivity.

The Host-Side Hardware Interface

At the physical hardware level, modern BMC system-on-chips (SoCs)—such as the ASPEED AST series—include an integrated 2D graphics controller alongside the management processor. This graphics controller exposes itself to the server's central processing unit (CPU) over the PCI Express (PCIe) bus as a standard VGA-compatible display adapter.

Because the device presents standard PCI configuration registers, the host’s BIOS/UEFI firmware and operating systems (such as Linux or Windows Server) treat it as a native, local graphics card. The host loads standard display drivers and writes video data directly to the memory-mapped frame buffer allocated for this adapter, entirely unaware that the device is managed by an auxiliary controller.

Frame Buffer Capture and Differential Encoding

The BMC’s internal silicon bridges the display output to the management environment through memory sharing:

  1. Shared Frame Buffer: When the host OS renders text or graphics, the display controller writes the raw pixel data to dedicated video RAM (VRAM) or shared system RAM managed by the BMC.
  2. Video Capture Engine: The BMC features a built-in hardware capture engine that continuously scans the frame buffer for modifications.
  3. Differential Compression: Rather than constantly encoding and transmitting the full display at 60 frames per second, the capture engine calculates differences between frames (dirty rectangles). It compresses only the regions of the screen that have changed using hardware-accelerated algorithms, such as modified JPEG, run-length encoding (RLE), or H.264 video compression. This minimizes both network bandwidth and BMC CPU utilization.

KVM-over-IP Transmission

Once the display data is captured and compressed, the BMC’s internal operating system (typically an embedded Linux distribution like OpenBMC) packages the video frames into network payloads.

The BMC streams this data across the dedicated out-of-band management network interface via secure protocols (such as WebSockets or TLS-encrypted TCP sockets). On the client side, modern BMC implementations render this stream directly inside a standard web browser using HTML5 Canvas and JavaScript APIs, eliminating the historical requirement for specialized client software or legacy Java applets.

Bidirectional Input Redirection

Display output represents only half of the remote console pipeline. To make the virtual VGA console interactive, the BMC simultaneously acts as a USB host controller to the main server. The BMC firmware emulates a standard USB composite device containing a keyboard and a mouse.

When a user interacts with the remote console window:

  • The web client captures mouse events and keystrokes.
  • Input events are sent over the network to the BMC.
  • The BMC translates these network packets into standard USB Human Interface Device (HID) reports.
  • The host operating system receives these signals as native hardware inputs, creating a seamless, low-latency remote interaction model identical to standing directly in front of a local physical monitor and crash cart.
