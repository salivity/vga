How Hypervisors Emulate VGA Hardware

Hypervisors emulate standard Video Graphics Array (VGA) hardware to provide broad, out-of-the-box display compatibility for guest operating systems during early boot processes or when specialized display drivers are absent. To accomplish this, virtualization platforms trap legacy memory-mapped I/O and port-based commands, replicate VGA internal registers and video memory structures in host software, and continuously translate legacy video modes into framebuffers that the host system can render.

The Role of Legacy VGA in Virtualization

Legacy VGA emulation acts as a universal fallback. Modern virtual machines often rely on paravirtualized display drivers (such as VirtIO-GPU or VMware SVGA) for hardware-accelerated 2D and 3D graphics. However, an operating system cannot utilize these advanced drivers during initial installation, BIOS/UEFI POST routines, or safe mode. Standard VGA provides a well-defined, backward-compatible specification dating back to 1987 that nearly every operating system natively supports without requiring external drivers.

Trapping I/O and Memory Access

Physical VGA cards interface with the CPU via designated I/O ports (typically 0x3C0 through 0x3DF) and specific memory addresses in the real-mode address space:

  • 0xA0000 to 0xAFFFF for graphical modes (e.g., standard 320x200 or 640x480).
  • 0xB0000 to 0xB7FFF for monochrome text mode.
  • 0xB8000 to 0xBFFFF for color text mode.

Hypervisors utilize hardware-assisted virtualization extensions (Intel VT-x and AMD-V) to capture access to these resources. The hypervisor configures the Virtual Machine Control Structure (VMCS) or Virtual Machine Control Block (VMCB) to trigger a "VM-exit" whenever the guest CPU attempts to read from or write to these port ranges or physical memory locations. When a VM-exit occurs, execution drops back to the hypervisor's virtual device model (such as the VGA device emulation in QEMU), which processes the instruction and updates the virtualized hardware state.

Emulating Internal Controllers and Video Memory

Standard VGA is not merely a linear framebuffer; it relies on complex internal state machines composed of multiple functional sub-controllers:

  • Sequencer Registers: Control clocking and mask planes.
  • Cathode Ray Tube Controller (CRTC): Generates timing signals, horizontal/vertical sync, and cursor locations.
  • Graphics Controller: Manages how the CPU interacts with the planar memory.
  • Attribute Controller: Governs color palette lookups and attribute combinations.

The hypervisor maintains software data structures representing each of these registers. In complex planar modes (such as standard VGA 16-color Mode 12h), 256 KB of video RAM is divided across four distinct 64 KB memory planes. Because writes to planar memory can involve bit-masking, rotation, and logical operations dictated by the Graphics Controller, the hypervisor's software device model parses the active register state to compute the correct pixel updates across these virtual memory banks.

Framebuffer Generation and Host Presentation

The guest OS expects the VGA adapter to send a video signal to a physical monitor. The hypervisor achieves this by parsing its internal virtual video memory and generating a linear 32-bit RGB buffer:

  1. Text Modes (Mode 03h): The hypervisor reads the character codes and attribute bytes from the virtual 0xB8000 buffer, matches the character to an internal font bitmap (often stored in the virtual ROM or Plane 2), and renders the individual glyph pixels into the host-side buffer.
  2. Standard Graphical Modes (e.g., Mode 13h): In packed-pixel 256-color modes, each byte maps to a color palette register (DAC). The hypervisor maps the single-byte indices to 24-bit or 32-bit true-color pixels based on the emulated DAC registers.

To preserve performance, hypervisors employ dirty-page tracking. Instead of parsing and rendering the entire display on every guest write, the hypervisor marks the memory pages backing the virtual VRAM as write-protected. When the guest writes to VRAM, a page fault triggers, marking that specific memory page or scanline as "dirty." The hypervisor schedules periodic display flushes, processing only the modified regions and updating the output window via host graphical interfaces like SDL, GTK, VNC, or SPICE.

Handover to Secondary Display Engines

Because software-emulated VGA requires frequent VM-exits and complex planar calculation, it incurs high CPU overhead and provides low resolutions. As soon as the guest operating system finishes loading its kernel and base services, it detects any available virtualization-aware graphics adapters. The guest loads the corresponding paravirtualized or synthetic driver, which swaps legacy port I/O trapping for shared-memory command queues, effectively idling the legacy VGA emulator.
