How the Amiga Copper Was Simulated on PC VGA

The Commodore Amiga achieved revolutionary visual effects in the 1980s largely due to the "Copper," a dedicated hardware coprocessor synchronized with the monitor's display beam. While the Amiga manipulated display registers per-scanline with virtually zero CPU overhead, IBM-compatible PCs equipped with standard Video Graphics Array (VGA) hardware lacked any such coprocessor. To replicate Amiga-style raster effects, PC demoscene and game developers devised clever software techniques that hijacked the PC's central processor to manually "race the electron beam" using timing loops and hardware port polling.

The Amiga Copper Hardware Concept

The Copper (short for Coprocessor) was an integral component of the Amiga's original custom chipset, housed inside the Agnus chip. It functioned as an independent, programmable finite-state machine operating in complete lockstep with the video beam tracing across the CRT screen.

The Copper possessed a tiny but powerful instruction set consisting primarily of three operations:

  • WAIT: Pauses the Copper until the video beam reaches a specific horizontal and vertical beam position on the screen.
  • MOVE: Writes a 16-bit value into any hardware register within the custom chipset.
  • SKIP: Skips the next instruction if the beam is past a specific coordinate.

Because it operated independently of the main Motorola 68000 CPU, the Copper could alter display properties on a scanline-by-scanline basis without taxing the system. Its most common applications included changing the background color on every scanline to produce smooth gradient "copper bars," modifying color palettes mid-frame to display hundreds of distinct colors simultaneously, altering screen resolutions dynamically, and multiplexing sprites to bypass hardware limits.

The Architectural Limitations of PC VGA

When IBM introduced the Video Graphics Array (VGA) standard in 1987, it was designed primarily for business applications, text processing, and static graphics. Standard VGA featured no dedicated display coprocessor, no scanline interrupts, and no hardware mechanism to trigger register changes at specific screen coordinates.

VGA did, however, provide basic status feedback via I/O ports. Most notably, reading Input Status Register 1 (port 0x3DA) exposed two crucial bits:

  • Bit 3 (Vertical Retrace): Set to 1 when the electron beam finishes the frame and moves back to the top of the monitor.
  • Bit 0 (Display Enable / Horizontal Blanking): Toggled rapidly as the beam moved from the end of one scanline to the start of the next.

Simulating the Copper in Software on VGA

Without hardware support, PC developers had to simulate the Copper entirely in software by dedicating the host x86 CPU to act as a virtual Copper. Recreating these effects required strict real-time synchronization with the CRT beam:

1. Disabling Interrupts

To prevent erratic timing caused by system timers, keyboards, or background tasks, programmers executed the CLI (Clear Interrupt Flag) assembly instruction. This guaranteed the CPU dedicated 100% of its execution cycles to tracking the raster beam.

2. Polling for Synchronization

The CPU entered a tight loop reading port 0x3DA to detect the start of the Vertical Blanking Interval (V-Blank). This established a reliable starting frame reference point. From there, the CPU would poll the Horizontal Blanking (H-Blank) bit to detect the start of each individual scanline.

3. Cycle-Exact Timing and Racing the Beam

Polling port 0x3DA introduced slight timing jitter due to the varying clock cycles of the IN instruction and memory buses. Advanced programmers calibrated their code using cycle-exact assembly loops, filling execution gaps with precise sequences of NOP (No Operation) instructions to keep the CPU synchronized to the monitor's refresh frequency.

4. Mid-Frame Palette Manipulation

Once synchronized to the raster line, the CPU acted like the Copper’s MOVE command. It wrote directly to the VGA Digital-to-Analog Converter (DAC) registers via ports 0x3C8 (Palette Address Write) and 0x3C9 (Palette Data). By updating the color values during the narrow H-Blank window, developers produced smooth color gradients and split-palette effects across the screen, effectively breaking the standard 256-color limit per screen.

Trade-Offs of the Software Approach

While software simulation allowed PC games and demos to reproduce Amiga-quality raster bars, dynamic sky gradients, and split-screen menus, it carried significant drawbacks. On the Amiga, the Copper ran in parallel, leaving the CPU free for game physics and AI. On the PC, simulating the Copper consumed the entirety of the CPU's processing power while active, meaning game logic had to be suspended or tightly interleaved between scanline updates. Furthermore, differences in CPU clock speeds and bus architectures across PC clones often made these effects fragile and prone to graphical tearing or palette corruption if execution fell out of step with the display beam.
