How DOSBox Replicates VGA Timing for Demos

This article examines how the DOSBox emulator accurately reproduces internal Video Graphics Array (VGA) timing mechanisms to support complex PC demoscene effects. It explores the synchronization between CPU cycle counting, virtual cathode-ray tube (CRT) raster beam tracking, blanking interval status flags, and mid-frame register modifications. Readers will gain a clear technical understanding of how software-level emulation bridges the gap between modern multi-tasking host systems and cycle-dependent legacy hardware.

The Challenge of Demoscene VGA Programming

During the 1990s, PC demomakers pushed VGA hardware far beyond standard IBM specifications. Demos frequently bypassed standard BIOS routines to directly program the Cathode Ray Tube Controller (CRTC), Sequencer, and Digital-to-Analog Converter (DAC) registers. By tracking the CRT monitor’s electron beam in real time, programmers created effects such as horizontal copper bars, raster splits, fine pel panning, and unchained "Mode X" graphics. If an emulator miscalculates the timing of the electron beam by even a few clock cycles, these visual effects desynchronize, resulting in flickering, screen tearing, or complete program crashes.

Cycle-Based Virtual Timing Loops

DOSBox maintains temporal consistency by tying all simulated hardware subsystems to a central CPU cycle counter. Unlike real hardware, which executes instructions and generates video signals simultaneously across parallel silicon pathways, a modern CPU must execute these processes sequentially.

To solve this, DOSBox divides time into discrete execution slices determined by the user's cycles configuration or dynamic core settings. Every emulated x86 instruction consumes a predetermined number of virtual cycles. These accumulated cycles serve as the master clock for peripheral subsystems, including the Programmable Interval Timer (PIT 8253/8254) and the VGA controller, ensuring that software timers and rendering logic advance at identical, predictable rates.

Emulating the Raster Beam and Status Register 0x3DA

Many demo routines rely on "beam racing"—polling Input Status Register 1 (port 0x3DA) in a tight loop to detect the exact moment horizontal blanking (H-Blank) or vertical blanking (V-Blank) begins.

Instead of simulating an analog electron beam continuously, DOSBox calculates the beam's coordinates dynamically upon request:

  1. When the guest software reads port 0x3DA, DOSBox checks how many virtual CPU cycles have elapsed since the start of the current video frame.
  2. It divides these cycles by the total cycles required per horizontal scanline, which is derived from the emulated dot clock and CRTC horizontal timing registers.
  3. This calculation yields the exact virtual scanline (vertical position) and character clock (horizontal position).
  4. If the calculated position falls within the programmed blanking windows, DOSBox sets the corresponding retrace bits in the returned status byte.

Because this calculation happens on demand, time-sensitive polling loops receive cycle-accurate state changes without requiring the emulator to draw pixels in real time.

Mid-Scanline Register Updates and Palette Alterations

Effects like raster-based palette gradients (copper bars) alter the DAC color palette repeatedly during active display time. To display these correctly, DOSBox must not simply draw an entire frame at the end of a refresh cycle using the final state of the palette registers.

To handle these alterations, DOSBox tracks mid-frame state changes using slice-based or scanline-based rendering techniques:

  • Deferred Scanline Rendering: DOSBox renders the display scanline-by-scanline rather than full frames at once. When a CRTC or DAC register changes, the engine flushes and renders all scanlines completed up to that precise virtual timestamp using the prior register configuration.
  • Palette Change Buffering: If colors are modified during a scanline, the engine records the exact pixel clock offset at which the modification occurred. When that line is converted into pixels for modern display output, the palette transition applies only to the sub-scanline region drawn after that clock edge.

Synchronizing the PIT and VGA Vertical Retrace

PC demos frequently use the Intel 8254 Programmable Interval Timer (PIT) mapped to IRQ0 to trigger music routines and mid-screen raster interrupts in tandem with the display refresh rate (typically 60Hz or 70Hz).

DOSBox synchronizes the PIT and the VGA engine by deriving both timings from a common real-time reference. If the guest software reprograms the PIT to match the VGA frame rate, DOSBox aligns the IRQ0 firing events with the calculated V-Blank cycles. This synchronization prevents phase drift between background tracker music playback and visual transformations.

Advanced Emulation in Modern DOSBox Forks

While the standard DOSBox release provides scanline-accurate timing sufficient for most historical software, advanced forks such as DOSBox-X and DOSBox Staging implement dot-clock-level precision. These advanced implementations emulate internal VGA latches, pixel shift registers, and memory interleave wait-states. This micro-architectural accuracy allows even the most timing-sensitive demoscene edge cases—such as mid-scanline pel panning and 8-dot to 9-dot sequencer changes—to render identically to original hardware.
