How Doom Achieved 320x200 3D Graphics on 486 PCs

When id Software released Doom in 1993, rendering smooth, full-screen pseudo-3D animation at 320x200 resolution on a 486-class personal computer was considered a massive technical hurdle. The game achieved this milestone by pairing deliberate structural simplifications with aggressive low-level algorithmic optimizations. By using Binary Space Partitioning (BSP) trees to prevent overdraw, constraining level geometry to a 2.5D space, employing column-based rendering, and relying exclusively on fixed-point arithmetic and lookup tables, lead programmer John Carmack bypassed the severe CPU and bus bottlenecks of the era to maintain a fluid target rate of 35 frames per second.

The 2.5D Geometric Simplification

Rather than rendering arbitrary 3D polygons, Doom operated on a pseudo-3D ("2.5D") world model. Levels were defined as two-dimensional floor plans consisting of sectors with independent floor and ceiling height values. Crucially, all walls were strictly perpendicular to the floor, and no two rooms could exist directly on top of each other.

Because walls never tilted, perspective projection was dramatically simplified. The engine did not need to perform full 3D matrix transformations for every pixel. Instead, it projected a two-dimensional horizontal line for each wall segment and then scaled vertical slices based on their distance from the player's camera.

Eliminating Overdraw with BSP Trees

On a 486 PC, drawing a single pixel multiple times per frame (overdraw) degraded performance rapidly. Carmack solved this using a pre-calculated Binary Space Partitioning (BSP) tree. During level compilation, the map was recursively subdivided into convex sub-sectors.

At runtime, the engine traversed the BSP tree from front to back relative to the player's position in \(O(N)\) time. As walls were rendered from nearest to farthest, the engine tracked occupied screen columns using a 1D horizontal occlusion array. If a wall segment fell into a column that had already been filled by a closer surface, that segment was clipped or skipped entirely. Consequently, every visible wall pixel was drawn exactly once.

Column-Major Texture Mapping

Because walls were always vertical in screen space, drawing a textured wall required scaling a one-dimensional texture column into a one-dimensional screen column. The engine did not need complex polygon-filling algorithms or perspective-correct affine texture mapping across two axes simultaneously.

To maximize performance, wall textures were stored in system memory in column-major order rather than standard row-major order. This ensured that reading a vertical strip of texture data accessed contiguous memory addresses, avoiding cache misses and allowing tight inner loops to write pixels down the screen rapidly.

Fixed-Point Math and Lookup Tables

Many consumer PCs of the early 1990s—such as those equipped with Intel 486SX or older 386 processors—lacked a dedicated Floating-Point Unit (FPU). Floating-point operations had to be emulated in software, which was far too slow for real-time rendering.

Doom eliminated floating-point operations entirely, using 16.16 fixed-point arithmetic (16 bits for the whole number, 16 bits for the fraction) for all spatial coordinates and velocities. In addition, the engine relied heavily on precomputed lookup tables (LUTs) for trigonometric functions like sine and cosine, as well as light-diminishing tables (colormaps) that simulated depth lighting without dynamic per-pixel calculations.

Framebuffer Management in VGA Mode 13h

The game targeted standard VGA Mode 13h, which offered 320x200 resolution with an 8-bit palette (256 colors). Writing directly to VGA video memory over the standard ISA expansion bus was notoriously slow due to limited bus bandwidth.

To overcome this hardware bottleneck, Doom maintained an off-screen framebuffer in fast system RAM. The entire scene—walls, floors, ceilings, and sprites—was composed in this system memory buffer. Once rendering finished, the complete 64,000-byte frame was copied to the VGA video memory using highly optimized 32-bit rep movsd x86 assembly instructions, ensuring maximum data throughput across the expansion bus.
