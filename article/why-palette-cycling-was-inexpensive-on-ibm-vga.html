Why Palette Cycling Was Inexpensive on IBM VGA

Palette cycling, also known as color cycling, was a prominent graphical technique in late 1980s and 1990s computer games used to simulate animations like flowing water, flickering fire, and glowing lights without redrawing pixels. On original IBM Video Graphics Array (VGA) hardware, this technique was computationally inexpensive because it exploited the architecture of indexed color modes. Instead of modifying thousands of bytes in video memory across a slow system bus, the central processing unit (CPU) only needed to update a handful of color registers in the display hardware, allowing complex animations to run with virtually zero performance overhead.

The Indexed Color Architecture

The efficiency of palette cycling stems from VGA's primary 256-color display mode, Mode 13h (320×200 resolution). In this mode, video random-access memory (VRAM) does not store raw red, green, and blue (RGB) values for each pixel. Instead, each byte in the 64,000-byte framebuffer acts as an 8-bit index pointing to an entry in a 256-color lookup table.

This lookup table is managed directly by the VGA hardware’s Random Access Memory Digital-to-Analog Converter (RAMDAC). As the video hardware scans through memory to generate the video signal, the RAMDAC intercepts each pixel's index number, retrieves the corresponding 18-bit RGB value (6 bits per channel) stored in its internal registers, and converts that value into the analog signal driving the CRT monitor.

The ISA Bus Bottleneck

On early IBM-compatible personal computers, the CPU communicated with the graphics card over the Industry Standard Architecture (ISA) bus. The ISA bus was notoriously slow, typically operating at 8 MHz with high wait states. Transferring data to VRAM was one of the most significant performance bottlenecks for game developers.

Redrawing a full 320×200 screen to animate an effect required transferring 64,000 bytes across this congested bus. Even updating a small portion of the screen demanded significant CPU cycles and bus bandwidth, leaving little computing power for game logic, sound processing, or physics.

Updating Registers Versus Updating Pixels

Palette cycling bypassed the video memory bottleneck entirely. Rather than changing the values of the pixels stored in VRAM, developers altered the RGB definitions inside the RAMDAC's palette registers.

To cycle colors, the CPU wrote to two specific I/O ports:

  1. Port 0x3C8 (Palette Address Write Mode Register) to specify which color index to modify.
  2. Port 0x3C9 (Palette Data Register) to write the new red, green, and blue values.

Shifting a range of 16 colors to create an animation loop required transferring only 48 bytes (16 colors × 3 color channels) through the I/O ports. Updating 48 bytes required a minuscule fraction of a millisecond, compared to the immense computational cost of updating tens of thousands of screen pixels.

Instantaneous Full-Screen Results

Because the RAMDAC references the lookup table dynamically on every single frame refresh, altering those few palette bytes instantly transformed every pixel on the screen associated with those indices. A developer could fill the entire background with thousands of animated waterfall or lava pixels, yet the CPU only executed a short loop of register writes during the vertical blanking interval. This separation of pixel data from color definitions made palette cycling one of the most powerful and computationally economical graphical tricks of the VGA era.
